# Implementation plan: federated hot leg over pgx (#719)

This plan builds the design in [design.md §6.1.1](design.md). The federated pass stops reading PostgreSQL through DuckDB. It reads the dirty set and the hot keys over pgx in one `REPEATABLE READ READ ONLY` snapshot, and DuckDB reads only the parquet tiers. Go merges the two results. Once this lands and #785 is in place, no Forma deployment needs `postgres_scanner`. #631 is then superseded, and #691 and #754 have nothing left to assess.

## Before the first change

Three inputs gate the work. The first two gate the switch of the default path, not the code.

- **The #728 ruling.** Under this design PostgreSQL filters the hot rows and DuckDB filters the parquet rows of one answer. Until each difference has a ruling and the ruling ships on both dialects, a row's inclusion depends on whether it has been flushed. The tier parity suite (step 6) fails on such a difference until then. #763 is ruled and needs no change on either dialect: a non-canonical rfc3339 image is outside the query contract, so the suite's fixtures hold canonical images only (`docs/rfc3339-storage-contract.md`).
- **The latency baseline** that #719 asked for. It measures how federated latency splits between the PostgreSQL copy and the parquet scan on today's path, with the benchmark harness, at several `entity_main` sizes for a fixed hot set. Steps 3 and 5 compare against it. Without it, "cheaper" in the design is a claim nobody has checked.

## Steps

Each step is one PR and leaves `main` releasable. Steps 1 to 5 change no answer, with two exceptions, both in step 2 and both on today's path too. The cursor normalization refuses a hand-built cursor whose boundary does not match its column's type. A cursor that names `deleted_ts` reads the column's NULL as `0`: on the rows that tie the cursor before that column, it admits the hot rows and live pre-#274 rows it drops today wherever it admits the rows holding `0` (ascending below or at `0`, descending at or above `0`), and it orders them by the later cursor columns instead of last (design.md §6.1.1 tabulates the boundaries). The new path stays off until step 6.

1. **The snapshot reader and the `change_log` index.** Replace `PostgresDirtyIDFetcher`'s strict fetch with a reader that, in one read-only `REPEATABLE READ` transaction, returns the dirty set for either tier form. The hot form reads the widened `flushed_at = 0 OR flushed_at >= cutoff`, the hot-excluded form the strict set. The reader also returns `HasParquetHistory` from the same snapshot. Add the `(schema_id, flushed_at)` index, including `row_id` and `changed_at`, to `init-db`. Measure staging the dirty set through the Appender against binding it as a `UUID[]` parameter, at 1,000, 10,000 and 100,000 ids. The result decides the transport in step 3. Validation: `EXPLAIN` in an integration test shows the dirty-set read using the index, and the result matches today's sets.

2. **Sort keys and the comparator, in Go.** Derive each hot sort key from its stored value by the CDC export's rules (design.md §6.1.1, the table under *Ordering parity*). Reuse #785's stage decode where it applies. Add the comparator, with `NULLS LAST` in both directions, and the three-valued keyset predicate. Both take the page's order as input: the offset form's `ORDER BY` with its `row_id ASC`, or the keyset form's cursor columns with each column's direction, `row_id` included (design.md §6.1.1, *The page's order*). Add the cursor normalization (design.md §6.1.1, *One boundary type per cursor column*) to `validateKeysetCursor`, where both transports pass, and render each keyset parameter as `CAST(? AS <export type>)`. Validation: a lockstep test writes rows that reach each derivation's edges, flushes them, and requires the parquet leg's values and `ORDER BY` order to match the Go derivation and comparator. Before writing the `DOUBLE` comparator, a test against DuckDB checks how the engine orders NaN and -0. A cursor parity test binds boundaries of every Go type a caller can pass against every export type: a `float64` 9.6 and whole floats on a `BIGINT` column, integers at 2^53 - 1, 2^53 and 2^53 + 1 and at the `BIGINT` limits on `BIGINT` and `DOUBLE` columns, a NaN boundary, and upper-case uuid text. Each boundary is either refused before either leg runs, or the rendered DuckDB predicate and the Go predicate admit the same rows. A tiebreak test does the same for both `row_id` directions: over rows that tie on every column before `row_id`, the Go comparator orders them as `buildKeysetOrderBy` orders them under `row_id ASC` and `row_id DESC`, and as `buildNonKeysetOrderBy` orders them, and the Go predicate at a `row_id` boundary inside the run admits the rows DuckDB admits.

   The same step applies the `deleted_ts` rule (design.md §6.1.1, *`deleted_ts` reads `0`*). The hot key derives as `0`. The shared keyset renderer references the column as `COALESCE(deleted_ts, 0)` in the predicate and the `ORDER BY`, and leaves the dedup window and the outer select alone. Validation, over one fixture whose live rows are in every encoding (hot, a parquet row exported since #274, and a pre-#274 delta row with a NULL `deleted_at`), on today's path now and on both transports from step 5:
   - *Keyset form.* Walk the fixture with cursors on `deleted_ts, row_id`, ascending and descending, at the boundary `0`, one row per page, and flush the hot rows between two pages. The walk returns every row exactly once, in `row_id` order. Before this step, both walks drop every hot row and every pre-#274 row.
   - *Boundaries.* One page per direction at the boundaries -1, 0 and 1, with `deleted_ts` leading, on the `attach` path, pins design.md's table row by row: ascending at -1 and descending at 1 return every row, the cursors at `0` the rows after their `row_id`, ascending at 1 and descending at -1 none. Each case asserts the NULL-encoded rows by name, since before this step the cases that admit rows return only the rows holding `0`. A cursor on `created_at, deleted_ts, row_id` over rows that share a `created_at` across the encodings pins the order change: the rows come back in `row_id` order, where today the NULL rows come last. The rendered predicate and the Go predicate admit the same rows at each of these boundaries.
   - *Offset form.* A request that sorts on `deleted_ts` is refused before either leg runs, so offset pages cannot reach the column. An offset walk over the same fixture, with the same flush between two pages, returns every row exactly once.

   **Decision point:** sort keys on list attributes. Either implement DuckDB's `LIST` order, or refuse such a sort on the federated route with a 4xx.

3. **The parquet-only template.** Add a template without `pg_source` and without the `ATTACH`. It reads `dirty_ids` from the staged set, renders explicit `NULLS LAST`, and takes its parquet window (`OFFSET max(0, offset-h)`) as a parameter. The plan-cache scope of this template drops the connection string and the dirty-set flag. Today's template stays. Validation: the §5 sketch test gains a parquet-only twin. The compiled-plan cache keeps one entry per shape, whatever the dirty set's size.

4. **The hot leg's PostgreSQL queries.** Add the hot-keys query: the PostgreSQL route's condition (`ToDualClauses`' PostgreSQL payload), restricted to `entity_main` rows with an entry in the dirty window, `ver_ts` from the newest entry. Add the page read by `row_id`, reusing the PostgreSQL route's reader. Validation: the condition-DSL parity cases run against the hot-keys query and the PostgreSQL route, and must select the same rows.

5. **Engine wiring, behind a switch.** Add `DuckDBConfig.HotLegTransport` (`attach`, the default, or `pgx`). The `pgx` pass runs the six steps of design.md §6.1.1: snapshot, sort, stage, DuckDB, merge, page read. The same step also changes the following:
   - totals and the #181 recount;
   - the keyset coordinator's cursor-free recount;
   - the frozen inventory (design.md §6.1.1): each glob of a source-authored path set is listed at resolution, and the scan reads the listed objects. A failed listing fails the pass as a degradable `ErrFederatedReadFailed`. A listed object deleted before the scan fails the read; its classification must not claim a manifest inconsistency (`ErrParquetSetInconsistent`), since no manifest listed it;
   - the #720 empty-set short-circuit;
   - the flush-grace cutoff on the `pgx` hot form: P minus `FlushVisibilityGraceMs`, with a negative value read as `0`, never `sqlgen.FlushGraceCutoffDisabled` (design.md §6.1.1, *The widening is never disabled on this path*). The `attach` transport and the hot-excluded form keep today's resolution. Engine construction logs once when a negative value meets `pgx`, and the comments on `DuckDBConfig.FlushVisibilityGraceMs` and `WithFlushVisibilityGrace` say that the negative value applies to `attach` only;
   - classification: snapshot failures are `ErrPostgresReadFailed` and stay out of the breaker;
   - the disjointness guard;
   - `HotLegMaxDirtyRows`;
   - the execution plan's sources: the hot leg is recorded as a PostgreSQL source whose predicate PostgreSQL evaluates, in place of `hot-leg predicate (evaluated in DuckDB)`;
   - metrics: a latency stage for the snapshot reads, and a hot-match count beside `fed_query_row_count{source="pg"}`. Both change `docs/telemetry.md`.

   Validation: the federated e2e suite and the production harness run under both values of the switch. A mixed-tier tiebreak test walks one run of rows that tie on every column before `row_id`, some hot and some in parquet with their `row_id`s interleaved, one or two rows per page so that page boundaries fall inside the run and between a hot row and a parquet row. It walks the run under `created_at DESC, row_id DESC` and `created_at DESC, row_id ASC` cursors with no `AttributeOrders`, under an attribute sort with its required `row_id ASC` cursor, and as offset pages. Each walk must return every row exactly once, in the order DuckDB gives the same rows once all are flushed. A regression test covers a flush that races the query with the widening configured off. It reuses `runRacedQuery`'s pause after path resolution (`cdc_flush_grace_e2e_test.go`) with `FlushVisibilityGraceMs = -1` and the `pgx` transport. The racing flush appends and marks between P and the snapshot. Two variants: one creates four new rows, and the page must hold all eight rows, where `DisabledWideningExposesRace` sees four on `attach`; the other updates four flushed rows, and the page must hold their new values, not the versions in the resolved set. A unit test pins the cutoff: under `-1`, the `pgx` hot form's cutoff is the path-resolution instant, and the hot-excluded form and `attach` still get `sqlgen.FlushGraceCutoffDisabled`. `DisabledWideningExposesRace` stays pinned to `attach`. The other e2e tests that set `-1`, `TestFlushManifestWindowVisibility` and `TestFirstFlushAfterTheEmptyScanCheckStaysComplete`, assert complete answers and pass under both transports. Under `pgx` the widening keeps the second test's marked rows in the hot leg. Its slow-clock twin, whose marks fall below any cutoff, then carries the #720 recheck's coverage on that transport. A regression test covers publication after the snapshot over a non-empty glob. A schema read through the level-3 glob has parquet objects. A test hook between the snapshot and the DuckDB scan updates one clean row and flushes it, and deletes and flushes another. The page must hold the first row at its snapshot version and still hold the second.

6. **Parity and the default.** Add the tier parity suite: each condition-DSL case over the same rows before and after their flush must match the same rows. Add a dual-run test that answers each request under both transports and requires equal pages, order and totals. Its fixtures put rows in every tier, at every sort-key edge from step 2, in runs that tie across the tiers on every key before `row_id`, walked with both `row_id` directions, in each `deleted_ts` encoding with the step 2 walks and boundary cases, and in the flush race (a mark landing between path resolution and the snapshot). A publication after the snapshot is not a dual-run fixture: today's path has no snapshot to hold it to, so step 5's regression test checks it against the snapshot version instead. Flip the default to `pgx` once both pass with #728 shipped. Rolling back is setting the switch to `attach`.

7. **Retire the attach path.** Remove the `attach` value, `pg_source`, the `ATTACH`, its guard and `queryWithPostgres`, the catalog alias, the DuckDB consumer of the main-table fragment, and `postgres_scanner` from the federated client's required steps. Replace `TestHotLegCopiesWholeTables` with a test that the federated client neither loads `postgres_scanner` nor attaches. Then update the docs: design.md §5, §6.1 and §7.5 describe the new path, §6.1.1 folds into them, and `aurora-dsql.md` drops the extension row. Close #631, #691 and #754 with a pointer here.

## Risks

- **Parity gaps the suites miss.** A predicate or ordering difference that no fixture reaches splits answers by tier silently: a row appears or disappears, or changes position, when it is flushed. The suites are the only guard, so fixtures come from the condition-DSL catalogue and from every derivation row, not from examples.
- **Hot rows that now fail the read.** A hot row whose stored image the OLTP read refuses (#708, #592) fails a federated page that answered before. The PostgreSQL route already fails on that row. Run the census before flipping the default, and repair what it reports.
- **Connection use.** A `pgx` pass holds one pooled PostgreSQL connection for its whole duration, DuckDB included. Size the pool for concurrent federated passes before flipping the default. If that is not affordable, use the re-read-and-retry variant from design.md §6.1.1.
- **A large backlog.** With CDC stalled, every pass reads and stages the whole dirty set. That is no worse than today, which copies all of `change_log`. `HotLegMaxDirtyRows` lets a deployment send such passes to PostgreSQL alone.

## Fallback

If the parity rulings or the tier parity suite stall, the alternative recorded in design.md §6.1.1 still removes `postgres_scanner`: stage the dirty rows in DuckDB over pgx and keep the merge there. Step 1, the staging half of step 3, and step 7 carry over. Steps 2, 4 and 6 are not needed for it.
